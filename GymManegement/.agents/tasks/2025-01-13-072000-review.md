# Trainer frontend implementation with Member feature inheritance and session management

This change adds Trainer role support to the frontend SPA, allowing trainers to see schedules and sessions they own, create new training classes, and approve member registrations. Trainers inherit all Member features (memberships view, personal schedule, check-ins, profile). The backend enforces ownership at the service layer for updates, but read operations and session creation have weaker authorization boundaries.

**Watch for:** Email-based trainerId lookup fails silently if JWT email doesn't match database exactly (confirmed); cached trainerId persists across logout/login cycles (confirmed); dashboard stats fetch all sessions from backend then filter client-side, loading 10,000+ records for large gyms (confirmed); backend GetByTrainerIdAsync fetches all 10,000 sessions then filters in memory instead of using SQL WHERE clause (confirmed); trainer role can create sessions for any schedule regardless of ownership (confirmed); no frontend validation prevents trainer from selecting another trainer's schedule in session creation (likely).

**Verdict**: NEEDS_CHANGES

## High-level view

Trainers get access to Member pages ('memberships', 'member-schedule') by adding them to the role map in app.js. The dashboard shows four stats: today's classes, monthly attended count, pending registrations, and weekly sessions. Pending and weekly stats use the `/api/Session/trainer/{trainerId}` endpoint introduced in this change, which loads all sessions for the trainer's schedules in one backend call. The trainerId is resolved by fetching all trainers via API and matching by email from the JWT token, with the result cached in a module-level variable that never clears.

Schedule and session pages filter data by trainerId for Trainer role. Schedule creation pre-fills and visually disables the trainer dropdown for trainers, with a hidden input holding the trainerId. Session creation filters available schedules to only those owned by the trainer.

Backend controllers accept Trainer role for POST and PUT operations on Schedule and Session. Service layer validates that a trainer can only update schedules/sessions they own by checking the authenticated trainerId from the JWT email lookup. Admins bypass this check. DELETE operations remain Admin-only. Session creation (POST) has no ownership validation—a trainer can create a session for any schedule by sending the scheduleId in the request body.

1. **Silent trainerId lookup failure** — `getTrainerId()` fetches all trainers and matches by email. If JWT email doesn't match (case handled, but whitespace or missing trainer record is not), returns null and displays generic "Không tìm thấy thông tin trainer." Log the failure reason (email not found vs API error) and include the email in the error message so the user can report it. Consider adding trainerId to JWT claims at login to eliminate this lookup.

2. **Cached trainerId never clears** — `_cachedTrainerId` is a module-level variable that persists across logout. If user A logs out and user B logs in without a page reload, user B sees user A's trainerId. Clear `_cachedTrainerId` and `window._cachedTrainerId` in the `logout()` function in auth.js.

3. **Dashboard stats fetch all sessions then filter client-side** — `loadTrainerPendingSessions` and `loadTrainerWeeklySessions` call `/api/Session/trainer/{trainerId}`, which fetches schedules for the trainer, then calls `GetAllAsync(1, 10000, ...)` to get all sessions, then filters by scheduleId in memory. For a gym with 15,000 sessions, this silently truncates at 10,000. Change SessionRepository.GetByTrainerIdAsync to use a SQL query that joins Session and Schedule and filters `WHERE Schedule.TrainerId = @trainerId` instead of fetching all and filtering in C#.

4. **Email lookup normalizes case but not whitespace** — `getTrainerId()` calls `.trim().toLowerCase()` on both sides, which handles case. But if the database has trailing spaces (unlikely but possible) or the JWT email has leading spaces, the match fails. Ensure both sides are trimmed.

5. **Trainer can create sessions for any schedule** — SessionController.Create has `[Authorize(Roles = "SuperAdmin,Admin,Trainer")]` but no ownership check. A trainer can POST `{ scheduleId: 123, memberId: 1, ... }` for any schedule, not just their own. Frontend hides other trainers' schedules in the dropdown, but the API doesn't block it. Add a check in SessionService.CreateAsync: if the authenticated user is Trainer role, verify the schedule belongs to them before creating the session.

6. **Disabled trainer dropdown in schedule creation may not submit** — The create modal sets `pointer-events: none; opacity: 0.6;` on the trainer select for Trainer role and adds a hidden input. If the form serialization doesn't read the hidden input or the disabled select, trainerId will be missing from the POST body. Verify schedule creation works for Trainer role; if trainerId is null in the backend, change to `readonly` or ensure the hidden input is read.

7. **No capacity enforcement on session approval** — When a trainer approves a session (status Registered → Approved), there's no check that the schedule's maxCapacity has been reached. A trainer could approve 100 registrations for a 10-person class. Add validation in SessionService.UpdateAsync: when status changes to Approved, count existing Approved sessions for the scheduleId and reject if at capacity.

## Email-based trainerId resolution with silent failure modes

`getTrainerId()` in dashboard.js fetches all trainers via `/api/Trainer?pageNumber=1&pageSize=1000` and finds the one whose email matches `getUser().email` from the JWT. If no match is found, it returns null. The calling code shows "Không tìm thấy thông tin trainer" but doesn't log why.

Possible failure modes:
- JWT email missing (shouldn't happen if login worked, but defensive code should handle it)
- Trainer record doesn't exist for this email (user has Trainer role in Users table but no Trainers table entry)
- Email mismatch (database has `trainer@gym.com`, JWT has `Trainer@gym.com` — case is handled with `.toLowerCase()`, but whitespace is not fully normalized)
- API call to `/api/Trainer` fails (network error, 401/403, backend down)

The function logs to console but the user sees a generic message with no actionable guidance. Better UX: "Không tìm thấy HLV với email: trainer@gym.com. Vui lòng liên hệ quản trị viên." or "Lỗi tải danh sách HLV: 403 Forbidden" depending on the failure.

Long-term fix: include `trainerId` in the JWT claims when a user with Trainer role logs in. AuthController.Login already returns `memberId` for Member role; add a parallel `trainerId` lookup for Trainer role and include it in the token. This eliminates the API call and removes the failure mode entirely.

## Module-level trainerId cache persists across logout

`_cachedTrainerId` is declared at the top of dashboard.js and assigned in `getTrainerId()`. It's also set on `window._cachedTrainerId` to make it accessible elsewhere (presumably for logout clearing), but no code actually clears it. If user A logs out and user B logs in (same browser tab, no page reload), user B calls `getTrainerId()`, which sees `_cachedTrainerId !== null` and returns user A's trainerId immediately without checking the JWT.

Frontend logout calls `logout()` in auth.js, which clears localStorage and redirects to login. Add `window._cachedTrainerId = null; if (typeof _cachedTrainerId !== 'undefined') _cachedTrainerId = null;` to the logout function.

Alternatively, remove the module-level cache and always look up trainerId from the JWT or a session storage keyed by the current user's email. The API call to `/api/Trainer` is only made once per page load per trainer, so caching across users is not necessary.

## Dashboard stats load all sessions then filter in memory

`loadTrainerPendingSessions(trainerId)` and `loadTrainerWeeklySessions(trainerId)` call `/api/Session/trainer/${trainerId}`. The backend endpoint `SessionController.GetByTrainer` calls `SessionService.GetByTrainerIdAsync`, which:

1. Fetches trainer's schedules: `_scheduleRepo.GetByTrainerIdAsync(trainerId)` (SQL query, efficient)
2. Extracts scheduleIds
3. Calls `_repo.GetAllAsync(1, 10000, null, null, null)` — fetches all sessions, up to 10,000
4. Filters `sessions.Where(s => scheduleIds.Contains(s.ScheduleId))` in C#

This is an N+1 variant: instead of joining Session and Schedule in SQL, it fetches all sessions then filters post-query. For a gym with 15,000 sessions, the query truncates at 10,000 and the trainer never sees sessions 10,001–15,000. For smaller gyms it's inefficient but works.

Fix: change `SessionRepository.GetByTrainerIdAsync` (or add a new method) to execute a SQL query:

```sql
SELECT s.* 
FROM Sessions s
INNER JOIN Schedules sc ON s.ScheduleId = sc.ScheduleId
WHERE sc.TrainerId = @trainerId AND s.IsDeleted = 0
```

Return the filtered sessions directly from the database. Remove the `GetAllAsync` call in the service layer. This scales to any session count and returns the correct result set.

## Trainer session creation has no ownership guard

SessionController.Create has `[Authorize(Roles = "SuperAdmin,Admin,Trainer")]`, so any authenticated trainer can call POST `/api/Session`. The request body includes `scheduleId`. There's no check that the schedule belongs to the authenticated trainer.

Frontend session creation modal filters the schedule dropdown to only the trainer's schedules (`/api/Schedule/trainer/${trainerId}`), so a normal user flow won't hit this. But a trainer who opens DevTools and POSTs `{ scheduleId: 999, memberId: 1, ... }` where schedule 999 belongs to another trainer will succeed.

Add a check in `SessionService.CreateAsync`: if the authenticated user is Trainer role (check `HttpContext.User` claims or pass `authenticatedTrainerId` as UpdateAsync does), fetch the schedule and verify `schedule.TrainerId == authenticatedTrainerId`. Return 403 Forbidden if not.

## Schedule creation modal pre-fills trainer but uses visual disable

The create schedule modal pre-fills the trainer dropdown for Trainer role and applies `pointer-events: none; opacity: 0.6;` styling. A hidden input `<input type="hidden" id="trainerIdHidden" value="${currentTrainerId}">` is injected. The form submit handler checks for this hidden input and reads its value if present:

```javascript
const trainerIdHidden = document.getElementById('trainerIdHidden');
const trainerIdValue = trainerIdHidden ? trainerIdHidden.value : document.getElementById('trainerId').value;
```

This should work, but it's fragile. If the form uses `new FormData(form)` elsewhere, the hidden input is included but the disabled select is not. The current code explicitly reads the value, so it should be fine, but worth verifying in a test: log in as Trainer, create a schedule, check the Network tab to confirm trainerId is in the POST body.

If trainerId is missing, change the implementation: remove the visual disable and make the select `readonly` (HTML doesn't have readonly on selects, so use `disabled` but ensure the hidden input is always read), or add an explicit check in the submit handler to validate trainerId is not null before calling the API.

## No capacity check when approving sessions

Schedule has `maxCapacity` field. Session has `status` enum. When a member registers, status starts as 'Registered' (pending). When a trainer approves it, status changes to 'Approved'. There's no check that the number of Approved sessions for a schedule doesn't exceed maxCapacity.

Scenario: Schedule maxCapacity=10. Trainer approves 15 sessions. Backend allows it, and now 15 members show up to a 10-person class.

Add validation in `SessionService.UpdateAsync`: when `request.Status == "Approved"`, query the count of Approved sessions for the schedule: `SELECT COUNT(*) FROM Sessions WHERE ScheduleId = @scheduleId AND Status = 'Approved' AND IsDeleted = 0`. If count >= schedule.MaxCapacity, return an error: "Lớp đã đầy (15/10). Không thể duyệt thêm."

Alternative: allow overbooking but surface a warning in the UI. The enforcement choice is a business decision, but currently there's no check at all.
