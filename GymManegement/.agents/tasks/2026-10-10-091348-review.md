# Repository modernization and DTO alignment

TrainerRepository migrated from stored procedures to direct SQL following the MemberRepository pattern. Session DTO updated to match database schema (RegistrationDate instead of SessionDate, status values aligned). Schedule DTO cleaned up to remove MemberId and add missing ClassName and MaxCapacity fields. All changes target the core CRUD operations without adding complexity.

**Watch for:** (1) Schedule DTO still uses DateTime for StartTime/EndTime but test documentation shows string format like "06:00:00" and dayOfWeek field — DTO/test mismatch not resolved (confirmed). (2) TrainerRepository GetAllAsync pagination uses string interpolation for ORDER BY clause which permits SQL injection via sortBy/sortDir parameters (confirmed). (3) Session RegistrationDate defaults to DateTime.UtcNow in DTO which prevents SQL datetime out-of-range errors but may use .NET default if deserialization skips the field initializer (likely).

**Verdict**: NEEDS_CHANGES

## High-level view

TrainerRepository eliminated all stored procedure calls and replaced them with parameterized SQL queries matching the MemberRepository pattern. Soft delete (IsDeleted=1) is correctly implemented across all operations. INSERT uses OUTPUT INSERTED.TrainerId, UPDATE includes UpdatedAt timestamp management, DELETE is non-destructive. A new paginated GetAllAsync overload was added with search filtering.

Schedule DTO fields were corrected: MemberId was removed (Schedules don't belong to members, they belong to trainers and facilities), ClassName was added to match the database column, MaxCapacity was added with a default of 20. The database uses StartTime/EndTime as DATETIME columns, and the DTO uses DateTime properties, which is correct. However, the test documentation in COMPREHENSIVE_API_TEST.md shows tests using "dayOfWeek": "Monday", "startTime": "06:00:00", "endTime": "07:30:00" which won't work with the current DTO. The DTO is correct for the database schema; the test format is wrong.

Session DTO changed from SessionDate to RegistrationDate to match the database column name. Status values changed from Scheduled/Completed/Cancelled to Registered/Attended/Cancelled to match the database CHECK constraint. RegistrationDate now defaults to DateTime.UtcNow in the field initializer, which should prevent DateTime.MinValue from reaching SQL Server.

TrainerRepository's paginated GetAllAsync uses string interpolation to construct the ORDER BY clause with user-supplied sortBy and sortDir parameters. This is a SQL injection vector even though other parameters are parameterized.

## TrainerRepository stored procedure removal

All CRUD operations in TrainerRepository.cs now use direct parameterized SQL instead of stored procedures. GetAllAsync dropped the `sp_Trainer_GetAll` call and replaced it with `SELECT * FROM Trainers WHERE IsDeleted = 0 ORDER BY CreatedAt DESC`. GetByIdAsync, GetByEmailAsync, GetWithSchedulesAsync all migrated similarly. The pattern matches MemberRepository.cs: connection creation with `using var conn = _db.CreateConnection()`, inline SQL strings, Dapper's QueryAsync/ExecuteAsync.

CreateAsync builds an INSERT with OUTPUT INSERTED.TrainerId, sets CreatedAt/UpdatedAt to DateTime.UtcNow, and returns the entity with TrainerId populated. UpdateAsync sets UpdatedAt to DateTime.UtcNow and includes `WHERE TrainerId = @TrainerId AND IsDeleted = 0`. DeleteAsync performs a soft delete: `UPDATE Trainers SET IsDeleted = 1, DeletedAt = @DeletedAt WHERE TrainerId = @TrainerId`.

A new paginated overload `GetAllAsync(int pageNumber, int pageSize, string? searchTerm, string? sortBy, string? sortDir)` was added. It defaults sortBy to "TrainerId" and sortDir to "ASC", constructs a WHERE clause with optional LIKE filtering on FullName/Email/Phone, then uses OFFSET/FETCH NEXT for pagination. The total count query runs in the same batch using QueryMultipleAsync.

The problem: sortBy and sortDir are interpolated directly into the SQL string with `$@"... ORDER BY {sortBy} {sortDir} ..."`. If sortBy is "TrainerId; DROP TABLE Trainers--", it executes. This is a confirmed SQL injection vector. MemberRepository.cs has the same vulnerability, so the pattern was copied faithfully, including the flaw.

## Schedule DTO field corrections

CreateScheduleRequest.cs had MemberId as a field. The database schema shows Schedules table has TrainerId and FacilityId foreign keys, not MemberId. The git diff confirms MemberId was removed. ClassName and MaxCapacity were added. The current DTO has TrainerId, FacilityId, ClassName, StartTime (DateTime), EndTime (DateTime), MaxCapacity (int, default 20). This matches the database schema columns: TrainerId INT, FacilityId INT, ClassName NVARCHAR(200), StartTime DATETIME, EndTime DATETIME, MaxCapacity INT DEFAULT 20.

COMPREHENSIVE_API_TEST.md lines 412-417 show the test sending:
```json
{
  "trainerId": 1,
  "facilityId": 1,
  "dayOfWeek": "Monday",
  "startTime": "06:00:00",
  "endTime": "07:30:00",
  "maxCapacity": 20
}
```

This includes a dayOfWeek field (not in the DTO) and startTime/endTime as time-of-day strings (not DateTime). The DTO expects DateTime for StartTime and EndTime. If the test sends this format, model binding will fail or produce DateTime.MinValue. The DTO is correct for the database schema. The test format is incorrect. The plan.md file confirms this: the test format is wrong, and the correct format should use ISO 8601 DateTime strings like "2025-01-15T09:00:00". The test documentation needs updating.

## Session DTO RegistrationDate handling

CreateSessionRequest.cs changed from SessionDate to RegistrationDate. The diff shows the old version had `public DateTime SessionDate { get; set; }` and the new version has `public DateTime RegistrationDate { get; set; } = DateTime.UtcNow;`. The database schema shows `RegistrationDate DATETIME NOT NULL DEFAULT GETDATE()`. The DTO field name now matches the database column name.

The Status field changed from "Scheduled" default to "Registered" default. The database CHECK constraint enforces `Status IN ('Registered', 'Attended', 'Cancelled')`. The new default is correct.

The field initializer `= DateTime.UtcNow` should prevent the DTO from carrying DateTime.MinValue when RegistrationDate is not provided in the request JSON. When ASP.NET Core's model binder deserializes JSON without a registrationDate field, the field initializer runs during object construction, so RegistrationDate should be DateTime.UtcNow.

Corner case: if the JSON explicitly sends `"registrationDate": null`, the deserializer may set the field to default(DateTime), which is DateTime.MinValue. SQL Server DATETIME minimum is 1753-01-01, so DateTime.MinValue (0001-01-01) causes "datetime out-of-range" errors. The field initializer handles the omitted-field case. The service layer should add a guard to replace DateTime.MinValue before calling the repository. No service layer changes are in the diff, so the explicit-null case may still fail.

## SQL injection in pagination ORDER BY

TrainerRepository.GetAllAsync(pageNumber, pageSize, searchTerm, sortBy, sortDir) constructs:

```csharp
var sql = $@"
    SELECT * FROM Trainers 
    {whereClause}
    ORDER BY {sortBy} {sortDir}
    OFFSET @Offset ROWS FETCH NEXT @PageSize ROWS ONLY;
    ...";
```

If the caller passes sortBy = "TrainerId; DROP TABLE Trainers--", that string is interpolated directly into the SQL. Dapper's parameter binding doesn't apply here because sortBy is part of the query structure, not a value parameter. MemberRepository.cs has the same pattern. The fix is to whitelist sortBy against allowed column names and validate sortDir is exactly "ASC" or "DESC" before interpolation.
