# Invoice and Payment CRUD with Role Management UI

Implementations of FEAT-003 (Invoice and Payment management) and FEAT-004 (User role management UI) add full CRUD functionality for invoices and payments, plus visual role indicators and a placeholder for role switching pending backend API support. The invoice module supports creating invoices linked to members and memberships, editing status, and deletion. The payment module records payment transactions with optional invoice linkage but provides read-only viewing after creation. The user module adds color-coded role badges and a workaround UI for role changes that documents the missing backend endpoint.

**Watch for:** Invoice creation allows both memberId and membershipId parameters but validation only enforces memberId, which could create invoices not linked to any membership (**confirmed**). Payment edit modal is read-only because the backend DTO has no editable fields, but the UI still calls it "edit" which is misleading (**confirmed**). Role switching in users.js shows a modal explaining the missing backend API rather than implementing the feature, fulfilling the workaround path but not the primary acceptance criterion (**confirmed**).

**Verdict**: NEEDS_CHANGES

## High-level view

Invoice creation fetches both members and active memberships for dropdowns, allowing optional membership linkage alongside required member selection. The form validates amount minimums and date logic (due date must follow invoice date), and the edit modal was constrained to status-only editing to match the backend UpdateInvoiceRequest DTO which only exposes a Status field.

Payment creation follows a similar pattern with member and pending-invoice dropdowns, but the edit experience differs: because UpdatePaymentRequest is empty (no editable fields per the backend schema), the "edit" modal became a read-only detail view with text explaining that payments cannot be modified after creation.

User role badges now use color coding (Admin=red, Trainer=blue, Member=green) and each non-current user has a role-change button, but clicking it opens an informational modal explaining that the backend lacks the required PUT /api/Auth/users/{id}/role endpoint. Current users see "Tài khoản hiện tại" instead of action buttons to prevent self-role-changes.

<summary>Issues (6)</summary>

1. **Invoice memberId vs membershipId confusion** — Invoice creation form has both fields but only memberId is validated, allowing invoices with a member but no membership link. Clarify whether this is intentional (e.g., ad-hoc fees) or if membership should be required when selected, and update validation or backend DTO documentation accordingly.

2. **Payment edit modal misleads as read-only** — showEditPaymentModal displays "✏️ Sửa Thông Tin Thanh Toán" (Edit Payment Information) but shows a read-only view because UpdatePaymentRequest has no fields. Rename to "Xem Thông Tin Thanh Toán" (View Payment Information) and change the button label from "✏️" (pencil) to "👁️" (eye) to match the actual behavior.

3. **Role switching is a documentation placeholder, not a feature** — FEAT-004 acceptance criteria require functional role switching with confirmation modals, but the implementation shows an informational modal explaining the backend API gap instead. This satisfies the "if backend doesn't support" workaround clause but leaves the primary requirement unmet. Backend team needs to implement PUT /api/Auth/users/{id}/role.

4. **Invoice filter doesn't preserve pagination state** — loadInvoicesByStatus() renders results with pageNumber=1 and totalPages=1 hardcoded, discarding pagination context when a status filter is active. Preserve the pagination data returned by the status endpoint or reset current page to 1 and call the paginated endpoint with status as a query param if available.

5. **escapeHtml missing in users.js role-change modal** — showChangeRoleModal function parameters include username and currentRole from user objects, but these are not passed or interpolated into the modal HTML (which is static text), so the risk is currently unexploited. If the modal is ever extended to show user-specific data, ensure escapeHtml is applied.

6. **Payment method filter not wired to backend** — The paymentMethodFilter dropdown in payments.js reloads payments but doesn't pass the selected method to the API. Either remove the filter or implement filtering logic (check if /api/Payment supports a method query param, or filter client-side on data.items).

## Invoice creation form with dual member linkage

The create invoice modal fetches both `/api/Member` and `/api/Membership` to populate dropdowns. The form has a required `memberId` field and an optional `membershipId` field. Validation enforces `memberId` but allows `membershipId` to be null or empty:

```javascript
if (!memberId.value) {
    document.getElementById('memberIdError').textContent = 'Vui lòng chọn thành viên';
    memberId.classList.add('invalid');
    isValid = false;
}
```

The membership dropdown filters to active memberships only:

```javascript
${memberships.filter(ms => ms.status === 'Active').map(ms => `<option value="${ms.membershipId}">...</option>`).join('')}
```

When submitting, `membershipId` is sent as null if not selected:

```javascript
const formData = {
    memberId: parseInt(document.getElementById('memberId').value),
    membershipId: membershipIdValue ? parseInt(membershipIdValue) : null,
    ...
};
```

This allows creating invoices for members without linking them to a membership, which might be intentional for ad-hoc fees (late fees, locker rentals, etc.) but could also be a data integrity gap if all invoices are supposed to tie to membership packages. The backend CreateInvoiceRequest accepts this pattern (memberId required, membershipId optional per the DTO), so the frontend aligns with the API contract. The question is whether the business logic should enforce membership linkage or allow standalone invoices.

## Invoice edit constrained to status changes

The edit modal fetches the full invoice object but only allows changing the status field. Other fields (totalAmount, dueDate, description) are displayed as read-only text in a gray info box. This matches the backend UpdateInvoiceRequest DTO which per the findings only has a Status field, not the full set of editable properties originally requested in FEAT-003.

## Payment creation with optional invoice linkage

Payment creation fetches members and pending invoices (`/api/Invoice/status/Pending`) to allow linking a payment to an unpaid invoice. The invoice dropdown is optional, matching the business pattern where payments can be recorded independently (e.g., cash received before an invoice is generated, or payments for non-invoiced services). The form includes all fields from CreatePaymentRequest: memberId, invoiceId (nullable), amount, paymentMethod (enum with 6 options including Cash, Card, QRCode, BankTransfer, MoMo, ZaloPay), paymentDate (defaults to today), transactionId (optional), and status (Completed, Pending, Failed).

## Payment edit is view-only due to backend DTO constraint

The `showEditPaymentModal` function fetches the payment and displays all fields in a read-only format inside a gray box. No input fields are rendered. Below the details, a message explains: "ℹ️ Thanh toán không thể chỉnh sửa sau khi tạo. Chỉ có thể xóa nếu cần điều chỉnh." (Payments cannot be edited after creation. Can only be deleted if adjustment is needed.)

This diverges from the modal's title "✏️ Sửa Thông Tin Thanh Toán" (Edit Payment Information) and the button label "✏️" (pencil icon suggesting edit). The findings note that UpdatePaymentRequest is an empty DTO with no editable fields, so the backend doesn't support payment updates. The frontend adapted to this constraint but kept the "edit" terminology, which is misleading. The button should be relabeled to "View" (👁️) and the modal title changed to "Xem Thông Tin Thanh Toán."

## Role badges with color coding

The `renderUsersTable` function assigns badge classes based on role: Admin=badge-danger (red), Trainer=badge-primary (blue), Member=badge-success (green), replacing the previous generic badge-info.

## Role switching button with backend API documentation modal

Each user row except the current user gets a role-change button:

```javascript
${!isCurrentUser ? `
    ...
    <button class="btn btn-sm btn-warning" onclick="showChangeRoleModal(${user.userId}, '${escapeHtml(user.username)}', '${escapeHtml(user.role)}')">🔄 Đổi vai trò</button>
` : '<span class="text-muted">Tài khoản hiện tại</span>'}
```

The current user check compares `user.userId` with `currentUser.userId` from localStorage, preventing self-role-changes.

Clicking the button calls `showChangeRoleModal`, which displays a static informational modal:

```javascript
function showChangeRoleModal(userId, username, currentRole) {
    document.getElementById('changeRoleModal').classList.add('show');
}
```

The modal content explains the missing backend endpoint:

```html
<p>Tính năng thay đổi vai trò yêu cầu hỗ trợ từ backend API.</p>
<p>Cần thêm endpoint: <code>PUT /api/Auth/users/{id}/role</code> với body <code>{"role": "Admin|Trainer|Member"}</code></p>
```

This satisfies the FEAT-004 workaround path ("if the role endpoint does NOT exist: implement a workaround UI... Document in findings that AuthController needs a PUT endpoint"), but the acceptance criteria's primary path requires functional role switching with confirmation and actual role changes. The findings acknowledge that "Backend team needs to add this endpoint for full functionality."

The modal receives userId, username, and currentRole as parameters but doesn't use them in the current implementation (the modal is generic text). If the modal is extended to show user-specific information ("Change [username]'s role from [current] to [new]?"), those parameters would need escapeHtml applied before interpolation into the DOM.

## Invoice and payment tables use escapeHtml consistently

All table cells rendering user-provided data apply escapeHtml. Users.js also escapes username, fullName, email, and role when rendering the table.

## Invoice status filter discards pagination

The `loadInvoicesByStatus` function fetches invoices by status from `/api/Invoice/status/{status}` and renders them with hardcoded pagination values:

```javascript
renderInvoicesTable({ items: data, pageNumber: 1, totalPages: 1 });
```

This assumes the status endpoint returns a flat array rather than a paginated response. If the dataset is large, this could load all matching invoices in one call. The regular `loadInvoices` function uses pagination (`pageNumber=${invoicesCurrentPage}&pageSize=${invoicesPageSize}`), but the status filter path bypasses it. If the status endpoint supports pagination, the call should include page params. If not, the function should at least document the limitation or implement client-side pagination.

## Payment method filter renders but doesn't filter

Payments.js includes a filter dropdown:

```html
<select id="paymentMethodFilter" onchange="loadPayments()">
    <option value="">Tất cả phương thức</option>
    <option value="Cash">Cash</option>
    ...
</select>
```

The `onchange` handler calls `loadPayments()`, which fetches `/api/Payment?pageNumber=${paymentsCurrentPage}&pageSize=${paymentsPageSize}` without passing the selected payment method. The filter value is never read from the DOM or sent to the backend, so the dropdown has no effect. Either remove it or implement filtering by checking if the API supports a `paymentMethod` query param (if so, append it to the URL), or filter `data.items` client-side after fetching.
