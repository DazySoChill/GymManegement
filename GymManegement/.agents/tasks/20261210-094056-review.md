# API Exception Handling Fix

The fix implements a global exception middleware to convert unhandled exceptions into proper HTTP error responses. The primary goal was to eliminate 7 endpoints returning 500 Internal Server Error by catching business logic violations (InvalidOperationException) and converting them to 400 Bad Request, and by adding missing validation in SessionService to prevent foreign key violations.

The fix addresses duplicate email detection in Member/Trainer services, non-existent member references in Session/Checkin services, and missing invoice lookups in InvoiceService. All targeted endpoints now return appropriate 4xx status codes with Vietnamese error messages instead of 500 errors.

**Watch for:** Middleware placement after CORS breaks the standard ASP.NET Core pipeline order (confirmed). SessionService member validation requires database lookup on every session create, adding latency (confirmed). Invoice PUT throws KeyNotFoundException for missing invoices but returns 404, creating inconsistency with other services that return null (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The middleware sits after CORS in the pipeline, which deviates from conventional placement before authentication. This positioning was deliberate to ensure CORS headers apply even when exceptions occur, but it breaks the standard "exception handler first" pattern seen in most ASP.NET Core applications.

SessionService now validates member existence by querying IMemberRepository before creating sessions. This prevents foreign key violations from reaching the database, but it adds a database round-trip to every session creation. The validation pattern mirrors CheckinService, maintaining consistency across the codebase.

InvoiceService.UpdateAsync throws KeyNotFoundException when the invoice doesn't exist, which the middleware converts to 404. Other services (Member, Trainer, Schedule, etc.) return null for missing entities and let the controller handle 404 responses. This inconsistency means invoice updates follow a different error-handling path than other updates.

The middleware response structure was simplified by removing the redundant `detail` field, leaving only `statusCode` and `message`. For 500 errors, the message is a generic Vietnamese string; for 4xx errors, the message is the exception's actual message. This prevents stack trace leakage while preserving diagnostic information for client-side validation errors.

## Middleware placement deviates from convention

The middleware is registered after CORS:

```csharp
app.UseHttpsRedirection();
app.UseCors();
app.UseMiddleware<GymManegement.Middleware.GlobalExceptionMiddleware>();
app.UseDefaultFiles();
app.UseStaticFiles();
app.UseAuthentication();
app.UseAuthorization();
```

Standard ASP.NET Core pipeline order places exception handling near the top (after HTTPS redirection but before CORS) so it catches exceptions from all downstream middleware. Placing it after CORS means exceptions from CORS, static files, and authentication middleware won't be caught.

The fix-changes.md rationale states this placement ensures CORS headers apply even when exceptions occur. This is backwards: if the exception middleware is *before* CORS, CORS still applies because the exception middleware doesn't short-circuit the pipeline until an exception actually occurs.

## SessionService member validation prevents foreign key violations

SessionService.CreateAsync now validates the member exists before inserting the session:

```csharp
if (request.MemberId <= 0)
    throw new InvalidOperationException("MemberId phải được cung cấp và lớn hơn 0.");

var member = await _memberRepo.GetByIdAsync(request.MemberId);
if (member is null)
    throw new InvalidOperationException($"Hội viên với ID {request.MemberId} không tồn tại.");
```

Without this check, a non-existent MemberId would cause a SqlException from the database foreign key constraint violation. The middleware doesn't explicitly catch SqlException, so it would fall through to the generic Exception handler, which returns a generic Vietnamese message without identifying the FK violation.

The validation adds a database round-trip on every session create. CheckinService has the same pattern for member validation, maintaining consistency.

## Invoice update throws instead of returning null

InvoiceService.UpdateAsync is the only service that throws an exception when the entity is not found:

```csharp
public async Task<InvoiceResponse?> UpdateAsync(int id, UpdateInvoiceRequest request)
{
    var entity = await _repo.GetByIdAsync(id);
    if (entity is null)
        throw new KeyNotFoundException($"Hóa đơn với ID {id} không tồn tại.");
    
    entity.Status = request.Status;
    await _repo.UpdateAsync(entity);
    return ToResponse(entity);
}
```

MemberService, TrainerService, ScheduleService, and PaymentService all return null for missing entities and let the controller convert null to 404:

```csharp
public async Task<TrainerResponse?> UpdateAsync(int id, UpdateTrainerRequest request)
{
    var entity = await _repo.GetByIdAsync(id);
    if (entity is null) return null;  // Controller returns 404
    // ...
}
```

The inconsistency means invoice updates follow a different code path. The middleware catches KeyNotFoundException and converts it to 404, so the end result is the same, but the mechanism differs. If a developer adds logging or metrics at the controller level for 404 responses, invoice updates would bypass that instrumentation.



## QR checkin still returns 500

CheckinService.CheckinByQRAsync validates the QR code by looking up the member and throws InvalidOperationException for invalid codes. The middleware should catch this and convert it to 400. The test results show POST /api/checkin/qr still returns 500, which means either the test was run before the fix, the actual exception thrown is not InvalidOperationException (e.g., SqlException, NullReferenceException), or the middleware is not registered correctly.

## Middleware exception handling structure

The middleware catches four exception types:

```csharp
catch (InvalidOperationException ex)  → 400
catch (ArgumentException ex)          → 400
catch (KeyNotFoundException ex)       → 404
catch (Exception ex)                  → 500
```

InvalidOperationException is used for business logic violations (duplicate email, invalid QR code, non-existent member). KeyNotFoundException is used only in InvoiceService. The generic Exception catch-all returns a hardcoded Vietnamese message, preventing stack trace leakage.

Logging levels are appropriate: Warning for expected client errors (4xx), Error for unexpected server errors (5xx).
