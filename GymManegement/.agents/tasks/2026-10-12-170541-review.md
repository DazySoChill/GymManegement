# Auto-create Trainer/Member records on user role assignment

This change solves the "Không tìm thấy thông tin trainer" error by ensuring that when a User is created with role Trainer (via `CreateStaffAsync`) or when a User's role is changed to Trainer or Member (via `UpdateUserRoleAsync`), the corresponding Trainer or Member record is automatically created in the database. The approach mirrors the existing auto-creation logic for Members during registration: check for an existing record by email, create if missing, wrap in try-catch to prevent User creation from failing.

**Watch for:** Possible race condition in QRCode generation (likely), duplicate email constraint violation if Trainer/Member repositories don't enforce unique emails (confirmed), Console.WriteLine logging that won't persist in production (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The change adds ITrainerRepository to the constructor (fixing a duplicate _memberRepo and _config assignment), then adds two auto-creation blocks: one in `CreateStaffAsync` for Trainer-role users, one in `UpdateUserRoleAsync` for both Trainer and Member roles. Each block checks for an existing record via `GetByEmailAsync` before inserting. Both blocks are wrapped in try-catch that logs to Console but doesn't rethrow, preserving the success of the User creation. The SQL migration backfills missing records for existing users, using a NOT EXISTS check to avoid duplicates and generating sequential QRCodes for Members via ROW_NUMBER.

The QRCode generation logic in `UpdateUserRoleAsync` uses `IDENT_CURRENT('Members') + 1` to predict the next MemberId, which is the same pattern used in `RegisterAsync`. This assumes no concurrent inserts and that the identity sequence is never reset. The SQL migration uses `MAX(MemberId) + ROW_NUMBER()` which is safer for bulk inserts but has the same concurrency gap. Neither approach is transactionally safe against concurrent Member creation.

The Trainer/Member repositories' `CreateAsync` methods are assumed to enforce unique email constraints (either via database unique index or application-level check). If they don't, the duplicate-check via `GetByEmailAsync` could pass but the insert could fail. The try-catch will swallow the error, but the User will exist without a corresponding Trainer/Member record, leaving the database in an inconsistent state.

The Console.WriteLine calls won't persist logs in a production environment that uses structured logging (Serilog, NLog, etc.). The warnings will be lost unless someone is watching console output, making it difficult to diagnose auto-creation failures post-deployment.

<summary>Issues (3)</summary>

1. **QRCode race condition** — `IDENT_CURRENT('Members') + 1` is not concurrency-safe. If two `UpdateUserRoleAsync` calls execute in parallel, both will see the same next MemberId and generate duplicate QRCodes. Use a database-level unique constraint on QRCode or generate QRCodes after insert using the assigned MemberId.

2. **Duplicate email handling unclear** — If Trainer/Member repositories don't enforce unique email constraints, `GetByEmailAsync` could pass but `CreateAsync` could fail on a duplicate email insert. The try-catch swallows the error, leaving the User without a Trainer/Member record. Verify that Trainers and Members tables have unique indexes on Email (IsDeleted = 0).

3. **Console.WriteLine in production** — Logging to Console.WriteLine won't persist in production. Inject ILogger and use structured logging so auto-creation failures are captured in the logging infrastructure.

## ITrainerRepository injection and constructor cleanup

The constructor previously had duplicate assignments for `_memberRepo` and `_config`. The diff removes the duplicates and adds `ITrainerRepository` injection.

## CreateStaffAsync auto-creation for Trainer role

After creating the User, if `user.Role == "Trainer"`, the method checks for an existing Trainer via `GetByEmailAsync` and creates one if missing. The entire block is wrapped in try-catch that logs to Console.WriteLine but does NOT rethrow. If auto-creation fails (duplicate email, repository error, database constraint), the User creation still succeeds and returns a UserResponse. The caller has no indication that the Trainer record is missing.

This preserves the existing behavior where User creation is the primary operation and role-specific records are secondary. The alternative (rethrow and fail the User creation) would break the contract but would prevent inconsistent state.

## UpdateUserRoleAsync auto-creation for Trainer and Member roles

After updating `user.Role`, the method checks the new role and auto-creates Trainer or Member records if missing. For Member role, it queries `IDENT_CURRENT('Members') + 1` to predict the next MemberId and pre-generates a QRCode as `M{nextMemberId:D6}` before inserting. If two role-change operations execute in parallel, both will see the same next MemberId and generate duplicate QRCodes. The Member table likely has a unique constraint on QRCode, so the second insert would fail. The try-catch would swallow the error, the role change would succeed, but the Member record wouldn't exist. The User would have role "Member" but no Member record, breaking the FK contract that the frontend expects.

## SQL migration backfill logic

The migration inserts Trainer records for all Users with Role = 'Trainer' who lack them (NOT EXISTS on Email match), then inserts Member records for Role = 'Member' users who lack them. QRCode generation uses `ROW_NUMBER() OVER (ORDER BY u.UserId) + MAX(MemberId)`, which is safer than the C# approach for bulk inserts but still has a race condition if new Members are inserted between the MAX(MemberId) subquery and the INSERT.

The verification query joins Users with Trainers and Members by Email and flags mismatches. If a User's email was changed but the old Trainer/Member record wasn't updated, this query would flag a false positive.
